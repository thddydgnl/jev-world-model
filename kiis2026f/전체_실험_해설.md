## 1. 연구 질문과 배경

### 1.1 JEV란 무엇인가

JEV(`jev-1.13.0`)는 TypeSafe가 2026-09-15에 공개한 "System One" 판단 모델이다. 공개 인터페이스는 다음과 같다.

- **입력**: 상태(`state`, 텍스트 또는 JSON)와 질문 목록(`questions`).
- **질문 형식**: `choice`(연구자가 정한 서로 배타적인 선택지), `noul`(참일 확률), `score`(서열 수준).
- **출력**: 각 질문의 선택지 위 **확률**. 자연어 문장을 생성하지 않는다.
- 한 요청 안의 질문들은 같은 `state`를 공유하지만 서로 독립적으로 평가된다고 문서에 적혀 있다.
- 내부 구조(architecture), 학습 목표(RLCD라고만 소개), 내부 표현(latent)은 공개되지 않았다.
  그래서 이 연구는 **공개된 확률 인터페이스만** 쓴다. 내부 표현을 가정하거나 추출하지 않는다.
- 고객별 fine-tuning은 제공되지 않는다. 그래서 JEV는 항상 **frozen**(고정) 상태로 쓴다.
- 이용약관(MCA 2.3(b))은 JEV 출력으로 다른 모델을 학습시키는 증류(distillation)를 제한한다.
  그래서 학습 LLM(B·D)은 **환경(게임 엔진)의 정답만**으로 학습하고, JEV 출력은 학습에도 checkpoint 선택에도 쓰지 않는다.

출처: [`../아이디어.md`](../아이디어.md) §6.

### 1.2 이 연구가 묻는 것

**"JEV처럼 선택지 확률로 답하는 판단 모델을, 에이전트의 세계모델(world model)로 쓸 수 있는가?"**

세계모델은 "(현재 상태, 행동) → 다음 상태"를 예측하는 모듈이다. 에이전트는 행동을 실제로 하기 전에 세계모델로
결과를 상상해 보고 더 나은 행동을 고른다. 보통 LLM 세계모델은 다음 상태를 **문장으로 생성**한다(생성형).
JEV 방식은 "이 행동 뒤 열쇠는 어디에 있는가? A. 상자 안 B. 플레이어 손 …"처럼 **선택지로 묻고 확률을 받는다**(타입화).

[`../아이디어.md`](../아이디어.md) §4는 "세계모델"이라고 부르기 위한 **조작적 조건 세 가지**를 정했다.

1. 출력이 현재 상태의 분류나 행동 추천이 아니라 **미래 환경 사실**이어야 한다.
2. 같은 상태에서 행동이나 행동 순서를 바꾸면, 실제 결과 차이에 맞춰 **예측도 달라져야** 한다.
3. 예측이 목표와 분리돼야 한다. 물체 위치·문 상태 같은 예측은 **목표가 바뀌어도 재사용**할 수 있어야 한다.

### 1.3 처음 설계와 지금 설계

**처음 설계 (9/20, `아이디어.md`·`설계.md`)** — A/B/C 세 조건.

| 조건 | 세계모델 | 설명 |
|---|---|---|
| A | frozen JEV | 공개 API |
| B | 학습한 LLM (Qwen3-4B + LoRA) | JEV와 같은 질문·선택지에 확률로 답하도록 환경 정답으로 학습 |
| C | 없음 | 같은 정책의 선호만 따름 (No-WM) |

처음에 고른 구조는 **A4 "direct-horizon"** 이었다. 현재 상태와 행동열 전체를 한 번에 주고 "행동열을 다 한 뒤의 사실"을
직접 묻는 방식이다. 가짜 중간 상태를 만들지 않아 모순이 쌓이지 않는다는 이유였다. 후보로 검토한 다섯 구조는 다음과 같다.

| 후보 | 방식 | 판정 (9/20) |
|---|---|---|
| A1 | JEV 내부 latent로 다음 latent 예측 | latent가 공개되지 않아 불가 |
| A2 | 한 걸음씩 상태 변수를 예측하고 상태를 재구성해 다시 입력 (재귀) | 가능하지만 오류가 섞이는 비용이 커서 처음엔 보류 |
| A3 | 후보 미래 상태 중 고르기 | 후보를 누가 만드느냐의 문제로 보류 |
| **A4** | 행동열 전체 뒤의 사실을 직접 질의 | **처음 채택** |
| A5 | 성공 확률·가치만 예측 | 전이 모델이 아니라 보류 |

**이후 바뀐 것.** MVP 실험(9/21–22, §10.2–10.3)에서 A4(direct-horizon)가 조건 2(순서 민감성)를 통과하지 못했고,
A2(재귀 한 걸음 예측)가 세 조건을 모두 통과했다. 그래서 KIIS 설계부터는 **모든 세계모델이 재귀 한 걸음 예측**을 쓴다.

**KIIS 설계 (9/23, 사용자 제안)** — **2×2 + C**.

| | 학습 없음 | 환경 데이터로 학습 |
|---|---|---|
| **타입화 (JEV 방식, 선택지 확률)** | **A** JEV (frozen) · **B0** Qwen3-4B | **B** Qwen3-4B + LoRA |
| **생성형 (다음 상태를 글로 씀)** | **D0** Qwen3-4B | **D** Qwen3-4B + LoRA |
| 세계모델 없음 | **C** 기본 에이전트 (+ V2에서 **C_fm** 추가) | |

모든 에이전트는 같은 정책, 같은 후보 행동열, 같은 계획기를 쓴다. **세계모델만 다르다.**

이 설계가 답하려는 네 질문 ([`실험계획.md`](실험계획.md) §0):

| 질문 | 비교 |
|---|---|
| Q1. 세계모델을 붙이면 에이전트가 좋아지는가 | A·B0·B·D0·D vs C (v2부터 C_fm도) |
| Q2. JEV 방식(타입화)이 생성형보다 나은가 | B0 vs D0 (학습 없음), B vs D (학습) — 같은 Qwen, 질문 방식만 다름 |
| Q3. JEV 방식을 frozen JEV 대신 학습한 LLM으로 얻을 수 있는가 | A vs B, A vs B0 |
| Q4. 여러 step을 굴려도 예측이 유지되는가 | k = 1..4 step rollout 정확도 |

## 2. 환경: TextWorld 함정 world

### 2.1 TextWorld를 쓰는 방식

- Microsoft TextWorld 1.7.0의 **symbolic JSON backend**를 쓴다. 게임 상태가 "사실(fact)" 목록으로 관리된다.
  예: `at(P, r_0)` (플레이어가 방 r_0에 있음), `in(k_0, c_0)` (열쇠가 상자 안에 있음), `locked(d_0)`.
- **완전관측**: 에이전트와 세계모델은 현재 사실 전부를 본다. 부분관측(안 보이는 곳)은 없다.
- **결정론**: 같은 상태에서 같은 행동은 항상 같은 결과를 낸다. 실행할 수 없는 명령은 아무것도 바꾸지 않는다(no-op).
- **복사(branch)**: 엔진 상태를 복사해 "만약 이 행동을 하면?"을 실제로 실행해 볼 수 있다. 이것으로 정답 라벨을 만들고,
  oracle arm과 진단 도구가 실제 결과를 얻는다.
- **명령 catalog**: world마다 "문법상 가능한 명령" 전체 목록(`possible_admissible_commands`)이 있다.
  정책은 이 정적 목록에서만 명령을 고른다. **"지금 실행 가능한 명령 목록"(`admissible_commands`)은 정책에 주지 않는다.**
  그것을 주면 실행 가능 여부 판단이 공짜가 되어 세계모델이 할 일이 사라지기 때문이다.
- Native quest(게임 내장 목표)는 쓰지 않는다. 목표는 우리가 원자 사실의 조합으로 정의한다.

### 2.2 v1 함정 world (K1–K5에서 사용)

`src/env/worlds.py` `build_trap_world`.

```text
[방 A] ──(잠긴 문)── [방 B]
  플레이어
  상자(닫힘) 안에 열쇠
  받침대 위에 목표 음식(apple 슬롯)
  바닥에 미끼 음식(pear 슬롯)
```

- 방 2개(A는 서쪽, B는 동쪽), 두 방 사이의 문은 **잠김**. 열쇠는 **닫힌 상자** 안에 있고, 이 열쇠만 문에 맞는다(`match(key, door)`).
- **목표** (원자 3개): 목표 음식을 **들고**(`in(apple, I)`), 문이 **열려** 있고(`open(door)`), 플레이어가 **방 B**에 있기(`at(P, room_b)`).
  목표 문장 예: "Be located in the cellar, carrying the red apple, with the steel door open."
- **최적 해답 6단계**: 상자 열기 → 열쇠 꺼내기 → 문 잠금 해제 → 문 열기 → (어느 시점이든) 음식 집기 → 동쪽 이동.
- **함정**: `eat {목표 음식}`은 음식을 들고 있으면 언제나 실행되지만, 목표를 영원히 불가능하게 만든다(비가역).
  **미끼**: `eat {미끼 음식}`은 무해하다. "먹기를 다 피하는 것"과 "치명적인 것만 피하는 것"을 구분하려던 장치다.
  → **실제로는 모든 실험에서 함정이 한 번도 발동하지 않았다** (정책이 목표 음식을 먹으려 하지 않음). 그래서 비가역성에 관한 주장은 하지 않는다.
- 명령 catalog는 **40개** (예: `close steel door`, `drop brass key`, `eat red apple`, `examine oak table`, …).
- 상태 변수(§3) **6개**: 플레이어 방, 휴대 물체 3개(열쇠, 목표 음식, 미끼 음식)의 위치, 상자 개폐, 문 개폐.

**episode와 root.** 한 world에서 여러 시작 상태(root)를 만든다. reset 상태에서 **무작위 명령 0–2개**
(look/inventory/examine 제외)를 실행한 상태가 root다. 이미 목표를 만족한 root는 건너뛴다. world·root 생성용 난수 seed는
**20260921로 고정**되어 있어서, 정책 seed를 바꿔도 world와 root는 똑같다. 한 root에서 에이전트 하나가 목표를 이루거나
step 제한(cap, 30)에 걸릴 때까지 도는 것이 episode 하나다.

### 2.3 이름과 데이터 분할

같은 구조에 **물체 이름만 바꾼** world를 여러 개 만든다. 이름이 곧 분할 기준이다.

- **dev**: 개발 중에 계속 본 이름 4세트(`TRAP_NAMES`, 예: wooden box / brass key / oak table / steel door / red apple / ripe pear / workroom / cellar)로
  만든 12개 world (`t000`–`t011`, 4번째부터는 이름 뒤에 " 2", " 3"을 붙임). 디버깅, 파일럿, smoke 전용.
- **어휘 풀** (`TRAP_VOCAB`): 슬롯(용기, 열쇠, 받침대, 문, 목표 음식, 미끼 음식, 방)마다 단어 목록을 만들고,
  dev 단어를 모두 뺀 뒤 슬롯별로 **train 60% / val 10% / test 30%**로 나눈다 (`vocab_split`, seed 고정).
  슬롯당 단어 수: 대부분 train 14 / val 2 / test 8, 방은 22 / 4 / 10.
- world 하나 안에서는 **이름끼리 단어가 겹치지 않게** 뽑는다 (한 명령이 두 물체를 가리키지 않도록).

| 분할 | world id | 수 | 용도 |
|---|---|---:|---|
| dev | `t000`–`t011` | 12 | 파일럿(K1), smoke, 생성형 형식 예시 |
| train | `tr000`–`tr149` | 150 | B·D 학습 전이 |
| val | `va000`–`va019` | 20 | B·D checkpoint 선택, (v2) 보정 |
| test | `te000`–`te023` | 24 | 본 평가 (K4, K5) |

- **world 지문(fingerprint)**: world의 "초기 사실 + 물체 id·이름·종류"의 해시. 파일 해시를 쓰지 않는 이유는 TextWorld가 빌드할 때마다
  묘사 문장(`desc`)을 무작위로 쓰기 때문이다 (모델 입력과 전이에는 영향 없음). 206개 world의 지문을
  [`worlds_manifest.json`](worlds_manifest.json)에 고정했고, 모든 실행은 자기가 쓴 world의 지문을 기록한다.

### 2.4 v2 world (V 단계, K4v2·K5v2에서 사용)

v1 결과(§10.6)를 보고 과제를 다시 설계했다. `build_trap_world_v2`는 v1 world에 **레버**(켜고 끌 수 있는 변형)를 더한다.
레버를 모두 끄면 v1 world와 지문까지 같다.

| 레버 | 변형 | 의도 |
|---|---|---|
| T1 곁방 | 방 C를 방 A에 **닫힌(잠기지 않은) 둘째 문**으로 연결(북·남·서 중 world마다), 미끼 음식을 방 C로 | 실행은 되지만 목표와 무관한 열기·이동 |
| T2 미끼 열쇠 | 문에 맞지 않는 둘째 열쇠를 받침대 위에 | 어느 열쇠가 맞는지 예측해야 함 |
| T3 음식을 용기 안에 | 목표 음식이 **닫힌 둘째 용기** 안에서 시작 | 해답이 길어지고 무관한 열기·꺼내기가 늘어남 |

- 보정(§10.7) 결과 **v2 = T3만 켬**. 상태 변수 7개(상자 2개의 개폐가 됨), catalog 51개, **최적 해답 7단계**
  (상자 열기 → 통 열기 → 음식 꺼내기 → 열쇠 꺼내기 → 문 잠금 해제 → 문 열기 → 동쪽 이동; 앞의 두 꺼내기 순서는 바뀔 수 있음).
- v2 이름은 v1과 같은 어휘 분할에서 **새로 뽑는다** (`trap_names_v2`). 용기·열쇠·문·방을 두 개씩 뽑을 수 있게 했고,
  "key"와 "door" 같은 머리명사만 겹침을 허용한다. world id 앞에 v가 붙는다: `tv…`(dev), `trv…`, `vav…`, `tev…`.
- v2 test 이름 조합은 v1 test와 겹치지 않는다. test 이름은 train·val에 한 번도 나오지 않는다.
- **X1** 세트: v2 test와 **같은 이름**의 24개 world에 **T1+T2+T3**(곁방, 미끼 열쇠, 용기 속 음식)를 모두 켠 것.
  학습한 B·D가 본 적 없는 구조에서의 예측 정확도를 잰다. 상태 변수 9개, catalog 73개.
- **x1dev**: X1 구조를 dev 이름으로 만든 12개 world. smoke 전용이다 (test 이름을 미리 건드리지 않으려고).
- 지문은 [`worlds_manifest_v2.json`](worlds_manifest_v2.json)에 세트별로 고정: dev 12, train 150, val 20, test 24, x1 24, x1dev 12.

## 3. 상태 표현과 상태 변수

### 3.1 canonical state

`src/env/serialize.py` `canonical_state`. 엔진의 사실 목록을 모델에게 줄 JSON으로 바꾼다.

- `player_room`: 플레이어가 있는 방 id (예: `r_0`)
- `entities`: 등장하는 물체의 id, 이름, 종류 (예: `{"id": "c_0", "name": "wooden box", "type": "c"}`)
  종류: `r` 방, `d` 문, `c` 용기, `s` 받침대, `k` 열쇠, `f` 음식, `P` 플레이어, `I` 인벤토리
- `dynamic_facts`: 바뀔 수 있는 사실 (위치, 개폐, 잠금)
- `static_facts`: 바뀌지 않는 사실 (방 연결 `link`, 방향 `east_of`/`west_of`, 열쇠-문 짝 `match`)

사람이 읽는 문장 버전(`facts_readable`, `render_facts`)도 함께 준다. 예: "The brass key is inside the wooden box."
허용된 정보만 들어가도록 whitelist가 있다 (Phase 0에서 금지 키 0건 확인).

### 3.2 상태 변수(schema)

`src/agent/task.py` `state_schema`. 목표와 무관하게 **바뀔 수 있는 모든 것**을 변수로 정의한다.

| 변수 id | 종류 | 가능한 값 (선택지) |
|---|---|---|
| `v_player` | room | 모든 방 |
| `v_par_{물체}` | parent | `inventory`(손에 듦), `at:{방}`(방 바닥), `in:{용기}`, `on:{받침대}`, 음식이면 `gone`(먹어서 사라짐) |
| `v_mode_{용기·문}` | mode | `open`, `closed_unlocked`, `locked` |

- 선택지는 **타입상 가능한 값을 전부** 나열한다. 그래서 정답이 항상 선택지 안에 있다(MVP-A에서 위반 0건 확인).
- v1: 변수 6개 (방 1, 휴대 물체 3, 개폐 2). v2(T3): 7개 (개폐가 3). X1: 9개 (휴대 물체 4, 개폐 4).

### 3.3 예측에서 상태를 다시 만들기 — 전이 규칙은 넣지 않는다

`project_state(base, values, schema)`: 변수별 예측값으로 새 상태를 만든다.

- 변수가 정하는 사실은 예측값으로 **바꾸고**, 변수가 다루지 않는 사실은 **그대로 둔다**.
- 적용하는 규칙은 질문 설계에 이미 있는 "변수 하나에 값 하나"뿐이다.
- **"닫힌 상자에서는 꺼낼 수 없다" 같은 전이 규칙은 코드 어디에도 없다.** 연구자가 넣은 시뮬레이터가 성능을
  만들어 내면 안 되기 때문이다 (`아이디어.md` §7 A2의 경고).
- `read_schema_values`는 그 반대 방향: 상태에서 변수값을 읽는다. 예측과 정답을 변수별로 비교할 때 쓴다.
- **roundtrip 테스트**: 실제 상태에서 행동을 실행하고, 결과를 변수값으로 읽은 뒤, 그 값만으로 상태를 재구성하면
  엔진의 상태와 똑같아야 한다. v1 `tests/test_recursive_roundtrip.py`(24/24, 160/160), v2 `tests/test_v2_worlds.py`(15,172/15,172)로 확인했다.
  이것이 성립해야 "예측한 상태를 다시 입력으로 넣어 여러 step을 굴리는" 재귀가 가능하다.

## 4. 에이전트 공통 구조

모든 arm은 아래 구조를 공유한다. 달라지는 것은 §5의 "후보를 무엇으로 평가하는가"뿐이다.

### 4.1 한 step의 흐름 (receding horizon)

```text
실제 현재 상태 (완전관측)
   │
   ▼
정책 Qwen3-4B → 후보 행동열 K=8개 (각 길이 H=2)
   │
   ├─ C:     1순위 계획의 첫 행동을 그대로 실행
   ├─ C_fm:  실패한 적 없는 첫 행동 중 정책 순위가 가장 높은 것
   └─ 계획기 arm (validity, oracle, A, B0, B, D0, D):
          후보에서 prefix(길이 1..H)를 뽑아 → 실패 기억으로 거르고 →
          각 prefix를 평가(엔진 또는 세계모델로 끝 상태를 상상) → 효용 J 계산 → 최댓값
   │
   ▼
고른 prefix의 **첫 행동 하나만** 실제로 실행 → 실제 결과 관측 → 다음 step에서 처음부터 다시 계획
```

episode는 목표를 모두 만족하면 성공, 30 step(cap)을 다 쓰면 실패로 끝난다.

### 4.2 정책 (후보를 내는 LLM)

`src/agent/policy.py`. 모든 arm이 같은 정책을 쓴다.

| 항목 | 값 |
|---|---|
| 모델 | Qwen3-4B, bf16, thinking 끔 |
| 디코딩 | 샘플링, temperature 0.7, top_p 0.9, 최대 320 토큰 |
| 출력 | JSON `{"plans": [["cmd", "cmd"], ...]}` — 후보 K=8개, 각 길이 H=2 |
| 입력 | 현재 사실(읽기용 문장), 목표 문장, 정적 명령 catalog, **최근 10개 시도와 성공/실패** |
| 형식 오류 | 한 번 다시 요청(schema repair). 그래도 안 되면 catalog 앞 8개를 한 걸음 계획으로 쓰고(fallback) 기록 |
| catalog 밖 명령 | 버림 |
| 난수 seed | `정책 seed + crc32("world|root|step")` — **arm은 key에 없다** |

**seed key에서 arm을 뺀 이유 (K0).** 원래 코드는 key에 arm이 들어 있어서, 같은 상태에서도 arm마다 다른 후보를 받았다.
짝비교(같은 world·root에서 arm끼리 비교)의 잡음이 커진다. arm을 빼면 **같은 상태에서는 모든 arm이 같은 후보**를 받는다.
step 0에서는 모든 arm의 상태가 같으므로 후보가 완전히 같아야 하고, 실제로 매번 확인한다(K1 48/48, K4v2 smoke 9/9 arm).
LLM 세계모델(B, D)은 정책과 같은 가중치에 LoRA만 켜는데, **정책이 후보를 만들 때는 LoRA를 끈다** (`adapter_off`).
그래서 어댑터를 켠 프로세스에서도 후보가 같다.

**정책 프롬프트 (v1, 전문).**

```text
You control a deterministic text environment.
You are given the complete CURRENT physical facts, a goal, and a static
catalog of commands. A catalog entry is syntactically available but
may fail in the current state.

CURRENT FACTS:
{facts}

GOAL: {goal}

COMMAND CATALOG:
{catalog}

WHAT YOU ALREADY TRIED (oldest first):
{history}
A command marked FAILED did nothing: its preconditions were not met in the
state it was attempted from. Repeating it from an unchanged state will fail
again.

Return {k} distinct candidate command sequences, each of length {h}.
Order them by your preference for achieving the goal, best first.
Use only commands from the catalog, copied exactly.
Do not output predicted states, probabilities, explanations, or commands
outside the catalog. Do not assume a command succeeds merely because it is
listed.

Output JSON only: {"plans": [["cmd", "cmd"], ...]}
```

**v2 정책 레버** (V 단계에서 추가, 모든 arm 공통):

- **P1**: `CURRENT FACTS:` 앞에 일반 설명 한 줄.
  > NOTE: Closed containers and doors can be opened. A locked door or container must first be unlocked with the key that matches it. Objects can be inside closed containers and cannot be taken until the container is open.
- **P1′** (코드명 P1k): P1에 한 줄 더.
  > A key only works while you are carrying it: to unlock something, first take its key (for example out of an open container).
- **P2**: 같은 프롬프트를 두 번 샘플링해 계획을 합친다. 첫 샘플은 v1과 완전히 같은 호출(같은 seed)이고, 둘째 샘플은
  seed key `world|root|step#1`로 뽑아 **새 계획만** 뒤에 붙인다. 후보는 최대 16개.
- **v2 확정 설정(F2)**: P1′ + P2.

### 4.3 후보에서 prefix로

- 계획 8개 각각에서 길이 1과 길이 2의 앞부분(prefix)을 뽑고 중복을 뺀다 (`unique_prefixes`). 순서는 정책 순위를 따른다.
- **정책 사전값(prior)**: prefix를 포함하는 계획 중 가장 높은 순위를 [0, 1]로 바꾼다. 1순위 계획이면 1, 꼴찌면 0
  (`plan_prior = 1 − 순위/(계획 수 − 1)`).

### 4.4 효용 함수

```text
J(u) = conj + 0.25·progress − 0.1·E[무효 수] − 0.01·h + 0.05·prior
```

| 항 | 의미 | 계산 |
|---|---|---|
| conj | 상상한 끝 상태에서 목표 원자 3개가 **모두** 만족될 확률 | beam 가중 평균 (oracle은 0/1) |
| progress | 만족된 목표 원자의 비율 (0, 1/3, 2/3, 1) | beam 가중 평균 |
| E[무효 수] | prefix를 따라가며 **실행되지 않을** 명령 수의 기댓값 | 세계모델의 실패 확률 합 (oracle·validity는 실제 수) |
| h | prefix 길이 (1 또는 2) | 긴 계획에 아주 작은 비용 |
| prior | 정책 선호 | §4.3 |

- 계수 α=0.25, λ=0.1, c=0.01, β=0.05는 `설계.md` §11에서 정했고 **한 번도 튜닝하지 않았다**. test를 보고 고르면 누출이기 때문이다.
- **무효 항을 비율(`/h`)에서 개수로 바꾼 이유 (9/22, 조건 C3).** 원래 식은 `−λ·(무효 수)/h`였다. 이러면 길이 4짜리에 무효 2개가
  `−0.5λ`, 길이 1짜리에 무효 1개가 `−1.0λ`가 되어 **무효가 더 많은 긴 계획이 유리해진다**. H=4 실험에서 예측은 멀쩡한데
  (beam 포함률 99.2%) 성공률이 39.6%로 무너진 원인이었다. 첫 행동만 실행하므로 비교할 것은 "실패가 예상되는 양"이다.

### 4.5 실패 기억

`live_prefixes`. "이 상태에서 이미 시도해 실패를 본 행동으로 시작하는 prefix는 후보에서 뺀다. 모든 prefix가 그렇다면 그대로 둔다."

- 상태는 동적 사실 전체(지문)로 구분한다. 상태가 바뀌면 같은 행동을 다시 시도할 수 있다.
- 이 정보는 에이전트가 실제로 관측한 것이라 허용된다 (`설계.md` §3.5). 정책 프롬프트의 시도 이력과 같은 정보다.
- **왜 필요했나 (9/22, 조건 C2).** 재귀 arm R이 `take red apple`을 29번 반복했다. JEV가 0.91로 "실행된다"고 잘못 판단했는데,
  실행 안 되는 명령은 아무것도 바꾸지 않으므로 상태도 예측도 그대로라 같은 선택이 계속됐다.
- **K1에서 발견한 불공정 (9/23).** 실패 기억이 JEV arm에만 있고 validity·oracle에는 없었다. oracle이 무효인 `go east`를
  3–9번 반복하는 실패가 있었다. 모든 계획기 arm에 공통으로 넣고 validity·oracle을 다시 돌렸다 (commit `2323b8c`).
- **C에는 없다.** C는 계획기를 쓰지 않기 때문이다. 이 때문에 "세계모델 − C"에 실패 기억의 효과가 섞인다는 지적이 가능해,
  V2에서 **C_fm**(C + 실패 기억)을 추가했다 (§5, §10.7).

## 5. 비교하는 에이전트(arm) 전부

### 5.1 KIIS에서 쓰는 arm

| arm | 논문 표기 | 후보 평가 방법 | 세계모델 | 비고 |
|---|---|---|---|---|
| `C` | C | 평가 안 함. 1순위 계획의 첫 행동 | 없음 | 기본 에이전트 (No-WM) |
| `C_fm` | C_fm | 평가 안 함. 이 상태에서 실패한 적 없는 첫 행동 중 정책 순위 최상 | 없음 | **V2에서 추가**. C + 실패 기억 |
| `validity` | validity oracle | 엔진으로 실행 가능 여부만 확인. **목표 항을 0으로** (conj=progress=0) | 엔진(실행 여부만) | "무효 행동만 완벽히 거르면 어디까지 가나" |
| `oracle` | full oracle | 엔진으로 prefix를 실제 실행해 끝 상태로 conj·progress·무효 수 계산 | 엔진(완벽한 예측) | "같은 후보·효용에서 예측이 완벽하면 어디까지 가나" |
| `A_jev` | A | 재귀 한 걸음 예측, 타입화 질의 | JEV `jev-1.13.0` (frozen) | 이전 이름 R |
| `B0_typed` | B0 | 재귀, 타입화 | Qwen3-4B (학습 없음) | 선택지 글자의 다음 토큰 확률 |
| `B_typed` | B | 재귀, 타입화 | Qwen3-4B + LoRA | 환경 전이로 학습 |
| `D0_gen` | D0 | 재귀, 생성형 | Qwen3-4B (학습 없음) | 형식 예시 1개 |
| `D_gen` | D | 재귀, 생성형 | Qwen3-4B + LoRA | B와 같은 전이로 학습 |

- **oracle은 성능 상한이 아니다.** 같은 정책 후보와 같은 계획기(H=2, 근시안적 효용)에 완벽한 예측을 넣은 **진단 기준**이다.
  정책이 필요한 행동을 후보에 내지 않으면 oracle도 실패한다. 실제로 v1 test에서 oracle은 58.7%였다 (§10.6).
- **validity와 oracle의 차이**가 "실행 가능 여부를 넘어 결과까지 예측할 때 얻는 이득"이다.
  예: 후보가 `take dull key from table`(가짜 열쇠), `take brass key from wooden box`(진짜), `unlock … with brass key`(아직 열쇠 없음)라면
  validity는 셋째를 빼고 앞의 둘 중 정책이 선호한 쪽을 고른다. oracle은 둘째가 문을 여는 데 필요하다는 것까지 안다.

## 6. 세계모델 구조

### 6.1 재귀 한 걸음 예측 (모든 세계모델 공통)

`src/wm/recursive_forecaster.py` `RecursiveForecaster`. **세계모델에게는 언제나 "지금 상태에서 명령 하나"만 묻는다.**
여러 step은 예측한 상태를 다시 넣어 굴린다. JEV, Qwen 타입화, Qwen 생성형 모두 같은 코드를 쓰고
"한 걸음을 어떻게 묻는가"(`step` backend)만 바꾼다.

```text
beam = [(현재 상태, 가중치 1.0)]
prefix의 명령 a마다:
    beam의 각 상태 s(가중치 w)에 대해:
        한 걸음 예측 → (다음 상태 s', 실행 확률 p)
        실행된 가지  (s',  w·p)
        실패한 가지  (s,   w·(1−p))        ← 실행 안 되면 아무것도 안 바뀜
        이 깊이의 실패 질량 += w·(1−p)     → E[무효 수]에 더함
    가중치 0.02 미만인 가지 제거, 같은 상태끼리 합침, 상위 4개만 남기고 정규화
끝 beam에서 conj = Σ w·[목표 만족], progress = Σ w·(만족 원자 비율)
```

- beam 폭 4, 가지치기 0.02. 생성형은 실행 확률이 0 또는 1이라 사실상 beam 폭 1이다.
- **캐시**: (상태 지문, 명령)마다 한 번만 묻는다. episode 전체에서 공유한다 (같은 상황을 다시 묻지 않음).
- **배치** (`score_many`): 한 계획 step에 필요한 예측을 깊이별로 모아 한 번에 묻는다. Qwen을 GPU에서 효율적으로 쓰려는 것이고,
  prefix별로 따로 굴린 결과와 273/273 동일함을 확인했다 (`tests/test_batched_rollout.py`).
- **parity 테스트**: 엔진 정답을 돌려주는 가짜 backend를 끼우면 rollout이 실제 궤적과 같다 (48/48, `tests/test_rollout_parity.py`).
- 부수 기록: 어떤 변수의 최대 확률이 0.5 미만이면 "모순(contradictions)"으로 센다. 고치지 않고 세기만 한다.

### 6.2 타입화 질의 (A, B0, B)

(상태, 명령) 하나에 요청 두 개를 보낸다.

1. **상태 질문** (`R_step`): 모든 상태 변수를 선택지로 묻는다. 각 질문 앞에 공통 문구가 붙는다.
   > Starting from `current_state`, attempt exactly this one command: `{명령}`. Apply `rollout_convention`. Report the resulting state AFTER the command, not the current state. Question: {변수 질문}

   `rollout_convention`: "Attempt each command in `action_sequence` in order, starting from `current_state`. A command that cannot be executed in the state reached so far fails and changes nothing; continue with the next command. No new observations arrive during the sequence. Report the state after the whole sequence has been attempted."
2. **실행 여부 질문** (`R_valid`): **따로** 보낸다. 상태만 주고 행동을 시뮬레이션한다는 맥락은 넣지 않는다.
   > Consider the command below against `current_state` as it is now. Command: `{명령}`. Would this command actually execute, or would it fail because its requirements are not met in that state? Answer about whether it RUNS, not whether it is useful.

   선택지: `executes` / `fails`. 이 문구는 MVP-B2에서 91.6%를 낸 것 그대로다.

- **실행 여부를 따로 묻는 이유 (9/22, 동봉 오염).** 실행 불가한 명령(닫힌 상자에서 꺼내기)의 실행 확률이 단독으로 물으면 평균 0.285(10회 중 0회 0.5 초과),
  상태 질문 6개와 같은 요청에 넣으면 0.576(10회 중 8회 0.5 초과)이었다. 차이 +0.291, 표준오차 0.028.
  "명령을 실행했다고 치고 답하라"는 질문들과 같이 보내면 실행을 전제하는 쪽으로 판단이 샌다. 분리하자 순서 교환 검사가 4/18 → 14/18로 올랐다.
- 변수별 **argmax**로 다음 상태를 만들고, 실행 확률은 beam 분기에 쓴다.
- **JEV (A)**: TypeSafe API. 반환 모델이 `jev-1.13.0`이 아니면 중단한다. 원시 요청·응답을 `artifacts/jev_raw/`에 저장한다.
  요청 1회 비용은 약 $0.00007 (v1 K4: 23,758 요청에 $1.733).
- **Qwen 타입화 (B0, B)**: `LlmJudgeClient`가 JEV와 **같은 응답 JSON**을 만든다 (저장된 JEV 요청 60개로 계약 테스트).
  질문을 채팅 메시지로 바꾸고 선택지를 `A. [키] 설명`, `B. …` 글자로 나열한 뒤, "Answer with the letter of the correct option only."
  다음 토큰 분포에서 **선택지 글자들의 로짓만** 골라 softmax한 값을 선택지 확률로 쓴다. 생성은 하지 않는다.

### 6.3 생성형 질의 (D0, D)

- 시스템: "You simulate a deterministic text environment."
- **형식 예시 1개**: dev t000의 첫 상태에서 `open wooden box`를 실행한 예시(입력과 정답). D0·D 공통, K2에서 고정했고 v2에서도 그대로다.
- 사용자 메시지: `STATE:` + 타입화와 같은 상태 JSON(행동 포함) + 지시문:
  > Attempt the command in `action_sequence` once, starting from `current_state`, as `rollout_convention` describes. Reply in exactly this format and nothing else:
  > result: executes    (or: result: fails)
  > then every fact of the resulting state, one per line, written as predicate(argument, argument) with the ids used in `facts_canonical`.
- 디코딩: greedy, 최대 320 토큰. v2 정답은 최대 195토큰이라 여유가 있다.
- **파서** (`parse_generation`, 버전 v1):
  - 첫 줄이 `result: executes|fails`가 아니면 실패.
  - `fails`면 상태 유지 (뒤의 사실은 무시).
  - `executes`면 모든 상태 변수에 대해 사실 목록에서 **정확히 하나의 합법 값**이 나와야 한다. 없거나 둘 이상이면 실패 (추측하지 않음).
- 파싱 실패 시 **한 번 다시 생성**한다 (샘플링, T=0.7, top_p 0.9, seed는 (상태, 명령)으로 고정).
  그래도 실패하면 "실행 안 됨, 상태 유지"로 처리하고 파싱 실패로 센다. 실패한 답은 episode마다 5개까지 기록한다.
- 누출 테스트: 상태가 바뀌는 전이 89건에서 정답(다음 상태의 사실)이 어떤 형태로도 프롬프트에 없음을 확인했다.
  일부러 정답을 심으면 검출되는 것도 확인했다.
- 생성형에는 확률이 없다 (실행 여부 0/1). 이것도 두 방식의 차이에 포함된다.

### 6.4 LLM 세계모델과 정책의 가중치 공유

B0·B·D0·D는 정책과 **같은 Qwen3-4B 가중치**를 쓴다. B·D는 여기에 LoRA 어댑터를 얹는다.
세계모델로 쓸 때는 어댑터를 켜고, 정책이 후보를 만들 때는 끈다. 그래서 GPU 한 장에 프로세스 두 개가 들어가고
(프로세스당 약 9–14GB), 어댑터 유무와 관계없이 후보가 같다.

## 8. 지표, 통계, 진단 도구

### 8.1 closed-loop 지표 (표 1)

| 지표 | 정의 |
|---|---|
| 성공률 | 30 step 안에 목표 원자 3개를 모두 만족한 episode 비율 |
| steps | 실패 episode 포함 평균 step (최대 30) |
| 무효율 | 실행되지 않은 행동 수 / 전체 step |
| 파싱 실패율 | 생성형만: 재생성 후에도 파싱에 실패한 예측 / 전체 예측 |
| 세계모델 비용 | A: episode당 요청 수·$ / B0·B·D0·D: episode당 세계모델 GPU-초. 학습 GPU-h는 따로 |

- **독립 단위는 world**다. 같은 world의 episode들은 서로 닮았으므로, 신뢰구간은 world를 다시 뽑는 **world-clustered bootstrap**(4,000회)으로 낸다.
- **짝비교**: arm끼리 같은 (정책 seed, world, root)를 짝지어 차이를 낸다. 한쪽만 성공한 episode 수도 보고한다.
- 표본 크기 근거: 이전 3-seed 실행에서 A와 validity가 엇갈린 비율 18% → arm당 288 episode면 짝차이 CI 반폭 약 ±6%p.
- 해석 규칙: CI가 0을 포함하면 "이 표본으로는 구분되지 않는다"라고 쓴다. "동등하다"고 쓰지 않는다.

### 8.2 k-step rollout 지표 (그림 2)

rollout 하나 = (시작 상태, 길이 4 행동열). 모델이 closed-loop와 같은 재귀 beam으로 굴리고, 각 깊이 k=1..4에서 정답과 비교한다.

| 지표 | 정의 |
|---|---|
| **상태 완전일치** (주 지표) | k번째 행동 뒤 beam 1위 상태의 상태 변수가 **전부** 정답과 같은 비율 |
| 변수 정확도 | 변수 중 맞은 비율의 평균 |
| 실행 여부 정확도 | k번째 행동에 대해 (k−1)번째 beam 1위 상태에서 낸 실행 확률 ≥ 0.5를 판단으로 보고, **균형 정확도** (실행된 것·안 된 것 각각의 정확도 평균) |
| beam 포함률 | 정답 상태가 beam 안 어딘가에 있는 비율 |

- **persistence**: 아무것도 안 바뀐다고 예측하는 바닥선 (실행 확률 0 → 실행 여부 균형 정확도 50%).
- **파싱 실패 채점 (V2에서 수정)**: 생성형 응답이 파싱되지 않은 step부터 그 rollout의 이후 깊이는 **모두 틀린 것**으로 센다.
  K5 v1은 이 규칙이 구현되기 전이라, 파싱 실패의 대체값("상태 유지")이 실제로 상태가 안 바뀐 경우 맞은 것으로 셈해졌다
  (D0 과대평가 가능성, v1 기록으로만 둔다).
- **JEV 반복**: 같은 rollout 100개를 캐시 없이 3회 굴려 JEV 응답의 비결정성이 결과를 얼마나 바꾸는지 잰다.
- **오류 누적 (H8, 9/27 추가)**: 자유 rollout(free-running, FR)은 모델이 자기 예측을 다시 입력받아 굴러간다.
  **teacher-forced(TF)**는 매 step을 **실제 이전 상태**에서 한 걸음만 예측한다. 둘의 차이가 "자기 오류가 쌓여 생기는 오류"다.
  주 지표 누적 격차 G = k=2..4의 (TF_k − FR_k) 평균. 같은 Qwen에서 G(생성형) − G(타입화) > 0이면 타입화가 덜 쌓인다.
  타입화는 확률로 beam 4개를 들고 가고 생성형은 하나뿐이라, 타입화 Qwen을 **beam 1**로도 굴려 "형식"과 "beam"의 효과를 가른다.
  파싱 실패가 있었던 rollout을 뺀 G도 보고해 형식 오류와 내용 오류를 나눈다.
  K5 v1으로 탐색 계산하면 학습 전 Qwen에서 오히려 생성형이 덜 누적됐지만(조건부 정확도 B0 0.45–0.47, D0 0.47–0.66), v1은 파싱 실패 채점 결함이 있어 판단에 쓰지 않는다.

### 8.3 후보 커버리지 진단 (oracle이 왜 실패하나)

`scripts/kiis_k4_ceiling.py`. 모델을 호출하지 않고 저장된 로그만으로 모든 episode를 시작 상태부터 엔진에서 다시 재생한다.
재생한 모든 step의 실행 여부가 기록과 일치해야 한다 (일치하지 않으면 멈춤 — 기록 신뢰성 검사도 겸함).

- **유용한 행동**: 지금 실행 가능하고 해답 경로에 속하는 행동. 방 A에서는 상자·(v2) 통 열기, 열쇠·음식 꺼내기, 잠금 해제, 문 열기, 동쪽 이동.
  방 B(음식 없이 옴)에서는 서쪽 이동. (X1) 곁방에서는 방 A로 돌아가는 이동과 곁문 열기.
- 실패 episode를 **마지막 10 step** 기준으로 나눈다.
  - **후보 부족 (coverage)**: 정책 후보 중 유용한 행동으로 시작하는 것이 하나도 없었다 → 어떤 세계모델도 고칠 수 없음
  - **계획기 (planner)**: 유용한 첫 행동이 후보에 있었지만 고르지 않았다
  - **함정 (trap)**: 목표 음식을 먹었다 (전 실험 0건)

### 8.4 보정 기준 (v2 설계용, V1·V1b)

세계모델이 없는 arm(C, validity, oracle)만으로 과제·정책 설정을 고른다. 세계모델 결과는 보지 않는다.

| 기준 | 값 | 의미 |
|---|---|---|
| G1 | oracle 성공률 75–90% | 과제가 포화되지도 불가능하지도 않게 |
| G2 | oracle − validity ≥ 15%p | 실행 여부 이상의 예측이 성공률을 가른다 |
| G3 | 후보 부족 episode ≤ 5% (oracle) | 상한이 정책 후보에 막히지 않게 |
| G4 | C ≤ 20% | 계획이 필요한 과제 |

- 설정마다 dev 12 world × root 1 + val 20 world × root 2 = **52 episode**, seed 20260921, validity·oracle (C는 고른 설정에서만).
- 52 episode면 oracle 80% 근처에서 95% 구간 반폭이 약 ±11%p라 "거친 판정"이다. 본 실험 수치로 쓰지 않는다.
- 선택 규칙: 기준을 모두 만족하는 설정이 처음 나온 단계에서 멈추고, 그 안에서 oracle이 80%에 가장 가까운 것.
  아무것도 없으면 oracle − validity가 가장 큰 것을 고르고 미달을 기록한다. **기준은 옮기지 않는다.**

### 10.2 9/21 — MVP: JEV가 미래를 예측하는가, 세계모델이 쓸모 있는가

**Phase 0 (준비)**

- API 접근 확인: 인증, `jev-1.13.0` 고정 반환, 응답 형식 검증 — 통과.
- TextWorld smoke 11/11: 목표 없는 게임의 물리(리셋 후 미종료, 행동 후 상태 변화, 파서 실패는 no-op), 복사 격리(branch 실행 후 원본 불변, 재실행 결정론), 정보 whitelist(금지 키 0건).

**MVP-A (라벨 데이터)**

- 기본 world(방 2, 상자 속 열쇠, 받침대 위 방해물, 문 상태를 world마다 잠김/닫힘/열림으로) 8개 × root 4 = 32 root.
  root마다 행동열 6개 × h∈{1,2} = prefix 384개, 질문 5개 → 라벨 1,920개.
- 정답이 선택지 밖에 있는 경우 0, 상태 충돌 0, 대조 pair 844개. 독립 라벨러로 교차검증 0/384 불일치.
- 설계 의도 확인: 상자가 닫힌 root에서만 `open→take`와 `take→open`의 결과가 다름 (18:1 vs 0:13).

**MVP-B (JEV direct-horizon 예측력)** — 448 요청, 입력 1,119,380토큰, $0.047, 실패 0.

| 사전 고정 게이트 | 임계값 | 결과 |
|---|---|---|
| 0-step 현재 사실 추출 (입력을 제대로 읽나) | > 95% | **100.0%** (160/160) |
| 결과가 바뀐 사실에서 persistence 대비 | ≥ +10%p | h1 **+100%p**, h2 **+96.6%p** |

| 행동을 빼면 예측이 바뀌는가 (순반응성) | ≥ +30%p | **+87.4%p** |

- 네 게이트 모두 통과. 그런데 **사전 등록된 순서 교환 검사**(`open→take` vs `take→open`, 정답이 다른 18쌍)는 **0/18**이었다.
  `take→open`을 32번 모두 "열쇠는 손에"로 예측했다 (닫힌 상자라 꺼내기가 실패하는 19건 전부 오답). 정답 확률은 0.13–0.33으로 신호는 있으나 argmax가 틀림.
- 사후 분석 (탐색적): 행동열 안에서 엔진이 거부한 명령 수로 나누면

| h | 거부된 명령 | n | 정확도 |
|---:|---:|---:|---:|
| 1 | 0 | 525 | **100.0%** |
| 1 | 1 | 435 | 91.3% |
| 2 | 0 | 320 | **100.0%** |
| 2 | 1 | 410 | 90.2% |
| 2 | 2 | 230 | 82.6% |

- **배운 것**: 행동열이 정상 실행되면 완벽하다. 오류는 거의 전부 "실행 조건(precondition)을 어긴 명령"에 있다.
  당시 가설: "JEV는 명령이 항상 성공한다고 가정한다" (탐색적이라 확증된 주장으로 쓰지 않는다).

**MVP-B2 (실행 여부를 직접 물으면?)** — 32 root × 명령 10개 × 2조건 = 640 질문, 64 요청, $0.0058. 실행 가능/불가 50:50.

| 조건 | 정확도 | 가능한 것 맞힘 | 불가한 것 맞힘 |
|---|---:|---:|---:|
| V0 "지금 실행되나" | **91.6%** | 98.8% | 84.4% |
| V1 "명령 하나 뒤에 실행되나" | **92.2%** | 99.4% | 85.0% |

- 동사별: `unlock` 100%, `open` 100%, `take X from Y` 86.7%, `insert` 51.5% (최약점, 과제 경로에는 없음).
- 틀릴 때는 확신하고 틀린다 (불가한데 틀린 49건의 평균 실행 확률 0.76).
- **배운 것 (결론 수정)**: "JEV는 실행 조건을 판단할 수 있다. 다만 끝 상태를 묻는 질문에서는 그 판단을 적용하지 않고 성공을 가정한다."
  능력 한계가 아니라 **질문 형식**의 문제. → 실행 여부를 따로 묻는 설계로 이어짐.

**MVP-C (세계모델이 기여할 여지가 있나 — oracle headroom)** — 기본 world 12개(전부 잠긴 문, 5단계), 48쌍, cap 15, K=8, H=2, catalog 31.

| arm | 성공률 | steps | 무효율 |
|---|---:|---:|---:|
| C | 35.4% | 12.9 | 85.7% |
| oracle | **95.8%** | 6.7 | 14.6% |

- headroom +60.4%p (게이트 ≥ +10%p 통과), world 단위 10승 2무 0패.
- 선택한 행동이 실행 가능했던 비율 C 14.3% vs oracle 85.4%. C 실패 31건 중 26건은 진척 0 (열쇠도 못 얻음).
- 파일럿에서 정책이 시도 이력을 받지 못해 같은 무효 행동을 15번 반복했다 → **정책에 시도 이력 추가** (변경 1, 조건 C1). 파일럿 수치는 폐기.

**AB3 (validity-only arm)** — 무효 행동만 걸러 주는 arm을 돌리자, 쉬운 world에서는 headroom의 **97%가 실행 가능 여부**로 설명됐다
(oracle − validity = +2.1%p). 즉 쉬운 world에는 "결과 예측"이 필요 없었다.

**함정 world 재측정 (`mvp_c_trap`)** — 비가역 함정(`eat` 목표 음식)을 넣은 6단계 world, 12 × 4 = 48쌍, cap 20, catalog 40. **이것이 지금 v1 함정 world의 원형이다.**

| arm | 성공률 | steps | 무효율 | 진척 |
|---|---:|---:|---:|---:|
| C | 2.1% | 20.0 | 91.0% | 23.6% |
| validity | 70.8% | 11.3 | 15.3% | 85.4% |
| oracle | 91.7% | 8.2 | 25.4% | 95.1% |

- 예측이 필요한 몫(oracle − validity)이 +2.1%p(쉬운 world) → **+20.8%p**(23%)로 커졌다. 한쪽만 성공 episode 3:2 → 10:1.
- **그러나 함정은 한 번도 발동하지 않았다.** 격차의 실제 원인은 "문이 열린 뒤 `go east`/`go west`가 영원히 실행 가능해져,
  목표 정보가 없는 validity가 방 사이를 왕복한 것"이었다. 즉 **유효하지만 쓸모없는 행동**이 많아진 것이다.
- 교훈: 비가역성에 관한 주장은 할 수 없다. C가 2.1%로 붕괴 — 이 과제는 Qwen3-4B 혼자 풀기 어렵다.

**cap-40 통제** — step 예산 탓인지 확인: cap 20 → 40만 바꿈. C 6.2%, validity 75.0%, oracle 93.8%. 격차 +18.8%p 유지 → 예산 아티팩트가 아니다.
validity는 40 step을 줘도 25%를 실패한다 (느린 게 아니라 고르지 못함). 중간 집계(n=14)에서 격차가 0으로 보였던 것은 표본 잡음이었다.

**Arm A 본 실행 (`main_A`, 조건 C1)** — JEV를 계획기에 연결 (direct-horizon + 실행 패턴 분해 + 실행 여부 질문). 함정 world, cap 30, 48쌍.

| arm | 성공률 | steps | 무효율 |
|---|---:|---:|---:|
| validity | 75.0% | 13.4 | 10.9% |
| **A (JEV)** | **93.8%** | 10.6 | 38.2% |
| oracle | 97.9% | 8.4 | 23.1% |

- A − validity = +18.8%p (예측 구간의 82% 회수). world 단위 5승 7무 0패.
- A의 무효율이 validity보다 3.5배 높은데 성공률은 더 높다 → 이득이 실행 가능 여부 분류에서만 오지 않는다.
- JEV 10,927 요청, $0.891. conjunction 확률이 marginal들과 모순된 비율(Fréchet bound 위반) 14.7% — JEV joint 일관성의 결함.
- **사전 등록 예측 P1 "frozen JEV는 headroom의 상당 부분을 회수하지 못한다"는 기각됐다** (`docs/claims.md` B4, commit `edda2ef`에 고정).
  전제였던 "실행 조건을 모델링 못 함"이 MVP-B2에서 뒤집혔기 때문이다.

### 10.3 9/22 — 재귀 구조, 세계모델 조건 검증, 계획기 결함 수정

**arm A vs arm R (`R_full`, 조건 C2 = C1 + 실패 기억)** — 같은 48쌍.

| arm | 성공률 | steps | 무효율 | 요청/episode | 비용 | conjunction 위반 |
|---|---:|---:|---:|---:|---:|---:|
| A (direct-horizon) | 97.9% | 8.4 | 22.1% | 159 | $0.520 | 18.1% |
| R (재귀 한 걸음) | 95.8% | 9.9 | 32.9% | **61** | **$0.297** | **0%** |

- 차이 2.1%p는 episode 1개 (A만 성공 1, R만 성공 0) — 단일 seed에서 읽을 수 없는 크기.
- R은 요청이 A의 38%이고, conjunction을 묻지 않고 재구성한 상태에서 목표를 읽으므로 모순이 원리적으로 0이다.
- R의 깊이별 정확도: 상태 완전일치 depth 1 90.4% / depth 2 77.6%, 변수 정확도 98.4% / 95.7%, **진짜 상태의 beam 포함 100% / 100%**.

**세계모델 조건 검증 (`wm_criteria`)** — `아이디어.md` §4의 조건 2·3을 직접 측정.

| 조건 2: 순서 교환 18쌍 둘 다 정답 | 결과 |
|---|---:|
| direct-horizon (arm A) | **0/18** |
| 재귀, 실행 여부 질문을 상태 질문과 같이 보냄 | 4/18 |
| **재귀, 실행 여부 질문 분리** | **14/18** |

| 조건 3: 목표 독립성 | 결과 |
|---|---:|
| 같은 rollout을 다른 목표로 채점할 때 추가 호출 | **0** |
| 목표 1 / 목표 2 판정이 엔진과 일치 | 18/18 / 18/18 |

→ **arm R(재귀)은 세 조건을 모두 만족**, arm A(direct-horizon)는 조건 2·3 불만족. **KIIS에서 모든 세계모델을 재귀로 통일한 근거.**

**부수 발견 두 가지 (방법론)**

1. **JEV는 비결정적이다**: 같은 요청 12회 반복 시 실행 확률 0.15–0.37, σ ≈ 0.060. 한 번 측정한 비교는 믿을 수 없다.
   (실제로 한 번씩 비교해 "차이 없음"이라 판단했다가, 10회씩 다시 재서 뒤집힌 적이 있다.)
2. **동봉 오염**: 실행 여부 질문을 단독으로 물으면 0.285, 상태 질문 6개와 같이 보내면 0.576 (§6.2). 이 발견이 조건 2를 4/18 → 14/18로 바꿨다.

**질의 분해 ablation (`ablation`, 조건 C1)** — Aend(끝 상태만) **0.0%** (30 step 모두 소진, 무효율 96.2%), Aval(실행 여부만) **83.3%**, A(둘 다) 93.8%.
끝 상태 질문만으로는 아무것도 못 하고, 실행 여부 질문이 핵심이며, 둘을 합쳐야 가장 좋다.

**C1 조건 3-seed** — A 81.0% (seed 777, 34/42) / 88.6% (seed 1234, 39/44) / 93.8% (seed 20260921).
합친 A − validity **+13.4%p [4.1, 21.6]**, A − oracle −8.2%p [−14.9, 0.0].
seed 777·1234는 JEV **402 Payment Required**(크레딧 부족)로 48세트 중 42·44에서 끊겼다. **93.8%는 가장 운이 좋은 seed였다** — 단일 seed 수치를 쓰면 과대 주장이 된다.

**H=4 붕괴와 무효 패널티 수정**

- R을 H=4(길이 4 계획)로 돌리자 성공률 **39.6%**, steps 22.7 (조건 C2). 예측은 멀쩡했다 (beam 포함 99.2%).
- 원인 후보로 무효 패널티의 `/h`(비율 형태)를 찾아 개수 형태로 바꿈 (변경 3, 조건 C3). 그래도 H=4는 **31.2%** (`R_h4_fix`), H=2는 93.8% (`R_h2_fix`).
- 결론: H=4 붕괴는 예측이 아니라 **계획기** 문제다 (진척 동점, 근시안적 효용 등). 2쪽 논문에서 다룰 수 없어 **KIIS는 H=2로 고정**하고, 더 긴 상상은 k-step 정확도로만 잰다. 원인 분석은 fullpaper RQ3.

**C4 (실행 여부 질문 분리)** — 가장 좋은 예측 방식이지만 closed-loop는 H=1로 한 번만 돌았다 (`Rv2_h1`, 95.8%, 무효율 16.8%).

**조건 C1–C4 정리 (`docs/protocol.md` §A.4, `docs/paper_skeleton.md` §3.1)**

| 조건 | 추가된 것 | 측정된 것 |
|---|---|---|
| C1 | 정책에 시도 이력 | A 93.8% |
| C2 | + 계획기 실패 기억 | A 97.9%, R h=2 95.8%, R h=4 39.6% |
| C3 | + 무효 패널티 `/h` 제거 | R h=2 93.8%, R h=4 31.2% |
| C4 | + 실행 여부 질문 분리 | intrinsic 위주, closed-loop는 R h=1 95.8% |

결함을 하나 고칠 때마다 조건이 바뀌었는데 매번 전부 다시 재지 않아, **수치들이 서로 다른 조건에 흩어졌다**.
이 사고 때문에 KIIS에서는 조건을 하나(F)로 동결하고 전 arm을 새로 재며, 조건 해시로 섞임을 막는다 (§9).
**이전 closed-loop 수치는 표 1에 넣지 않는다.** 논문에는 예비 결과 하나(순서 교환 0/18 → 14/18)만 인용한다.

## 11. 사전 기대(가설) H1–H7과 판정

결과를 보기 전에 커밋한 기대다 (H1–H6은 K4 전 commit `3fa90d8`, v2에 그대로 재커밋; H1b·H7은 V2에서 추가).
**기대와 반대로 나와도 표와 그림은 그대로 싣고, 문장만 해석 규칙에서 고른다.**

| # | 기대 | 판정 방법 | v1 결과 (K4·K5) |
|---|---|---|---|
| H1 | 세계모델이 있는 에이전트(A, B, D)는 C보다 성공률이 높다 | 짝차이 95% CI 하한 > 0 | **성립** (+55.9%p 등) |
| H1b | A, B, D는 실패 기억만 있는 C_fm보다도 높다 | 짝차이 (A,B,D) − C_fm CI 하한 > 0 | v2에서 처음 판정 |
| H2 | 학습 없이는 타입화가 생성형보다 낫다 (B0 > D0) | 성공률 짝차이, k-step 정확도 | closed-loop **성립** (+6.6%p [0.6, 12.2]), 그러나 K5 rollout 완전일치는 D0 ≥ B0 — 엇갈림 |

| H5 | 같은 타입화 방식에서 JEV는 학습 없는 Qwen보다 낫다 (A > B0) | 성공률, k-step 정확도 | **성립** (+11.1%p; K5 k=1 91.0 vs 45.4%) |

## 13. 한계와 논문에서 조심할 점

**쓰지 않을 주장** ([`논문구성안.md`](논문구성안.md) §9에 정리)

- 타입화가 생성형 세계모델 **전반**보다 낫다 — 이 조건(Qwen3-4B 한 모델, 이 데이터, 이 파서)에서만 말한다.
- 다른 환경이나 실세계로 일반화된다 — TextWorld 한 과제 구조뿐이다 (+ X1 rollout).
- 학습한 LLM이 새 구조·과제에 일반화한다 — X1 범위에서만.
- 타입화의 이점이 "질문 형식" 자체에서 온다 — 확률·beam, 연구자가 정한 상태 변수 틀과 분리되지 않았다.
- JEV의 내부 표현이나 학습 목적(RLCD)이 원인이다 — 식별할 수 없다.
- CI가 0을 포함한다는 이유로 "동등하다".
- 긴 horizon 계획 — closed-loop은 H=2만.
- oracle을 "성능 상한"이라고 부르기 — 진단 기준이다.
- 비가역 행동이나 함정 — 함정이 발동한 적이 없다.
- 이전 조건(C1–C4) 수치를 표 1과 섞기, 보정 과정을 빼고 v2 결과만 보고하기, "최초".

**논문에 한 문장씩 밝힐 것**

1. 과제와 정책 지시문을 세계모델 없는 기준선만으로 dev·val에서 보정했다 (기준 G1–G4, 세계모델 결과는 보정에 안 씀).
2. 초기 과제(v1)에서는 모든 세계모델이 oracle과 같은 성공률에 붙어 비교가 안 됐고, 원인은 정책 후보 부족이었다.
3. test는 처음 보는 이름이지만 구조가 같다 (이름을 id로 바꾸면 test 전이의 76%가 train에 같은 구조로 있음). 새 구조는 X1로 따로 잰다.
4. B·D는 과제 구조의 전이 6,000개로 학습했고 JEV는 학습 없이 쓴다 — "frozen 범용 모델 vs 도메인 전이로 학습한 모델"의 비교다.
5. 학습 seed 1개, Qwen3-4B 한 모델, 연구자가 설계한 상태 변수 틀(스키마 설계 비용), 외부 API 의존(모델 버전 은퇴 시 재현은 저장된 원시 응답으로만).
6. JEV 응답은 비결정적이다 (K5에서 4.5% 칸이 회차마다 다름).
7. 정책 힌트(P1′)는 val 실패 분석에서 나온 일반 규칙이며 모든 arm에 같다.

**내부적으로 알고 있어야 할 것 (논문에 직역하지 않음)**

- val은 슬롯당 단어가 2개뿐이라 보정이 이름에 따른 정책 약점을 크게 반영했다. test에서 oracle이 75–90%를 벗어나거나 후보 부족이 다시 늘 수 있다 — 그래도 test를 보고 고치지 않는다 (K4v2에서 커버리지 진단을 함께 보고).
- 보정은 설정당 52 episode라 ±11%p 수준의 거친 판정이다.
- K5 v1의 D0는 파싱 실패 채점 결함으로 과대평가됐을 수 있다.
- v1 K4 smoke는 test world에서 돌았다 (결과 오염 없음 확인).
- v1 점검 스크립트를 지금 다시 돌리면 "로컬 검증 입력 = 서버" 한 항목이 false다 (K3 당시 코드와 비교하기 때문. v1 동작·해시는 불변).
- H=4 계획의 붕괴 원인은 풀지 못했다 (fullpaper RQ3).

## 16. 용어집

| 용어 | 뜻 |
|---|---|
| arm | 비교하는 에이전트 하나 (C, A_jev, B_typed …) |
| world | 이름이 정해진 게임 하나 (예: `te000`) |
| root | world 안의 시작 상태 하나 (reset 뒤 무작위 0–2걸음) |
| episode | 한 arm이 한 root에서 목표 달성 또는 30 step까지 도는 것 |
| 정책 seed | 정책 샘플링의 seed (20260921, 777, 1234). world·root 생성 seed와 별개 |
| step / cap | 에이전트의 실제 행동 한 번 / step 제한 (30) |
| 계획, 후보 | 정책이 낸 행동열 (길이 H=2, K=8개; v2는 최대 16개) |
| prefix | 계획의 앞부분 (길이 1 또는 2). 계획기가 평가하는 단위 |
| H / h / k | 계획 길이 / prefix 길이 / rollout 깊이 (그림 2) |
| catalog | world의 정적 명령 목록 (문법상 가능한 명령 전부) |
| admissible | 지금 상태에서 실제로 실행되는 명령 (정책에는 주지 않음) |
| 효용 J | 후보 평가 점수 (§4.4) |
| conj / progress | 목표 원자 전부 만족 확률 / 만족 원자 비율 |
| 실패 기억 | 같은 상태에서 실패한 행동으로 시작하는 prefix를 빼는 규칙 |
| 세계모델 | (상태, 행동) → 다음 상태 예측기 |
| 타입화 / 생성형 | 선택지로 묻고 확률을 받음 / 다음 상태를 글로 쓰게 함 |
| 재귀 rollout | 한 걸음 예측을 반복해 여러 step을 상상 |
| beam | 실행/실패 가지를 가중치와 함께 여러 개 들고 가는 방식 (폭 4) |
| direct-horizon | (옛 방식) 행동열 전체 뒤의 상태를 한 번에 묻기 |
| 상태 변수 (schema) | 바뀔 수 있는 모든 것 (방, 물체 위치, 개폐) — v1 6개, v2 7개, X1 9개 |
| canonical state | 모델에게 주는 상태 JSON (id·이름·사실) |
| 지문 (fingerprint) | world의 초기 사실·물체 정의 해시 |
| validity / oracle | 엔진으로 실행 여부만 아는 기준선 / 결과까지 아는 기준선 |
| headroom | oracle과 C(또는 validity)의 차이 — 세계모델이 채울 수 있는 여지 |
| 후보 부족 (coverage) | 정책이 필요한 행동을 후보에 아예 내지 않아 실패 |
| persistence | "아무것도 안 바뀐다" 예측 (k-step 바닥선) |

| 동봉 오염 | 실행 여부 질문을 상태 질문과 같이 보내면 판단이 실행 쪽으로 쏠리는 현상 |
